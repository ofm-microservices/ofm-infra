# Observability implementation results

Updated: 2026-08-17

## Implemented

- `run_id` and `scenario_id` are generated by the k6 runner and propagated through HTTP headers, gRPC metadata, Kafka headers, logs, and telemetry metadata.
- Shared Kafka propagation is implemented for all 12 Kafka service brokers; consumer tests and monolith migration tests pass.
- Zap JSON logs are collected by Vector and stored in ClickHouse; OTEL handles traces/metrics through Tempo and Prometheus, and Grafana queries all of them.
- JSON logging carries service, architecture, request/correlation, test-run, scenario, trace/span, operation, and duration fields.
- ClickHouse stores `ofm_load_test_runs` independently from log storage.
- Grafana dashboards are provisioned for overview, microservices, monolith, comparison, Kafka/projection, logs, traces, metrics, and load control.
- The load-test runner creates Kubernetes Jobs, passes run metadata, collects the k6 summary, queries monolith projection status, and persists the final verdict in ClickHouse.
- Runner control UI and Kubernetes Job start/stop API are available through the `experiment-service` ingress at `http://experiment-service.localhost`.

## Operational notes

- Grafana uses `test_run_id` as a bounded dashboard variable; dynamic request/entity IDs remain ClickHouse columns rather than metric labels.
- The runner UI is the reliable control surface for starting/stopping Jobs. Grafana links to that UI; Grafana itself does not execute arbitrary Kubernetes POST requests.
- The runner queries Prometheus for `sum(kafka_consumergroup_lag)` and `sum(ofm_kafka_dlq_messages_total)` when persisting a run. A zero value is valid when no lag or DLQ event exists; missing series are treated as zero by the runner.
- Automatic dashboard time-window navigation is represented by run metadata and the run variable; selecting a run does not yet change Grafana's global time picker automatically.

## Control and navigation behavior

- The Grafana Load Control dashboard links to the runner control UI, which provides Start and Stop actions for Kubernetes Jobs; cluster ingress/authentication remains an environment-level concern.
- Run-history `run_id` cells link back to the overview dashboard with `var-run_id`, `from=started_at`, and `to=finished_at`, so the selected run opens in its own time window.
